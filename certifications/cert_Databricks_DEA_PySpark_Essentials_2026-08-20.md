## 2. Definitions dictionary

| Term | Plain definition |
|------|------------------|
| **SparkSession** | Entry point: `spark`. Used to read tables/files and run SQL. |
| **DataFrame** | Distributed table with a schema (columns + types). Lazy until an **action**. |
| **Transformation** | Builds a new plan (`select`, `filter`, `join`) — does **not** run yet. |
| **Action** | Forces compute (`show`, `count`, `write`, `collect`). |
| **Lazy evaluation** | Spark waits to optimize the full plan before running. |
| **Column** | A named field; use `col("x")` or `df.x` in expressions. |
| **Schema** | Column names + data types (`StringType`, `IntegerType`, `ArrayType`, …). |
| **Shuffle** | Data moves across the network (joins, groupBy, repartition). Expensive. |
| **Broadcast join** | Copy the **small** table to every executor; avoid shuffling the big table. |
| **Skew** | One key has far more rows than others → one task runs forever. |
| **UDF** | User-defined function (Python). Flexible but usually **slower** than built-ins. |
| **Higher-order function** | SQL/PySpark functions that operate on **array elements** (`transform`, `filter`, `exists`). |
| **`spark.table`** | Load a registered table as a DataFrame. |
| **`spark.sql`** | Run a SQL string; returns a DataFrame. |

## 3. Core concepts (basics → exam depth)

### 3.1 Mental model (how Spark runs your code)

```
You write:  df.filter(...).select(...).groupBy(...).agg(...)
            ↓  (transformations = recipe only)
Action:     .write.saveAsTable(...)  or  .show()  or  .count()
            ↓
Spark optimizes the plan → splits work across executors → returns result
```

**Analogy:** Writing DataFrame code is like writing a **cooking recipe**. Nothing cooks until you put the pan on the stove (an **action**).

**Why the exam cares:** Questions often ask what happens **when** something runs, or why a job is slow (shuffle / skew / collect).

```python
from pyspark.sql import functions as F
from pyspark.sql.functions import col, lit, when, explode, broadcast, split
from pyspark.sql.types import IntegerType, StringType, DoubleType
```

### 3.3 Read data (bronze → DataFrame)

```python
# Unity Catalog / metastore table (preferred in Databricks)
bronze = spark.table("main.retail.orders_bronze")

# Same idea via SQL
bronze = spark.sql("SELECT * FROM main.retail.orders_bronze")

# Files (less common on DEA than tables, but know the pattern)
df = spark.read.format("json").load("/path/to/json")
df = spark.read.format("delta").load("/path/to/delta")
```

| API | Meaning |
|-----|---------|
| `spark.table("a.b.c")` | Load catalog.schema.table |
| `spark.sql("...")` | Run SQL; result is a DataFrame |
| `df.createOrReplaceTempView("v")` | Register DF so SQL can query it |

**FAQ:** `spark.sql` vs `spark.table`?  
- `spark.table` = “give me this table as a DF”  
- `spark.sql` = “run this SQL text” (can be any query)

### 3.4 Select, drop, rename, add columns

```python
# Keep / reorder / rename in one shot
df2 = df.select(
    col("order_id"),
    col("customer_id").alias("cust_id"),
    col("amount")
)

# Add or replace a column
df2 = df.withColumn("amount_eur", col("amount") * lit(0.92))

# Rename one column
df2 = df.withColumnRenamed("amt", "amount")

# Drop columns
df2 = df.drop("raw_payload", "_rescued_data")
```

**Analogy:** `select` is choosing columns for a report. `withColumn` is adding a calculated field on the spreadsheet.

**Exam traps:**
- `withColumn("x", ...)` **replaces** column `x` if it already exists.
- `alias` / `withColumnRenamed` only change **names**, not data.

### 3.5 Filter rows (WHERE)

```python
# Both are equivalent
active = df.filter(col("status") == "active")
active = df.where(col("status") == "active")

# Multiple conditions
ok = df.filter(
    (col("amount") > 0) & (col("country").isNotNull())
)

# SQL-style string (also valid)
ok = df.filter("amount > 0 AND country IS NOT NULL")
```

| Operator in PySpark | Meaning |
|---------------------|---------|
| `&` | AND (need parentheses) |
| `\|` | OR |
| `~` | NOT |
| `isNull()` / `isNotNull()` | null checks |
| `isin("A", "B")` | membership |

**Common mistake:** Using Python `and` / `or` instead of `&` / `|` → cryptic errors or wrong results.

### 3.6 Null cleaning & type casting (bronze → silver)

Official objective: *clean nulls, standardize data types, write silver*.

```python
silver = (
    bronze
    .dropna(subset=["order_id", "event_ts"])          # drop rows missing keys
    .fillna({"country": "UNKNOWN", "amount": 0.0})    # fill remaining nulls
    .withColumn("amount", col("amount").cast("double"))
    .withColumn("event_ts", col("event_ts").cast("timestamp"))
    .withColumn(
        "is_large",
        when(col("amount") >= 1000, lit(True)).otherwise(lit(False))
    )
)

silver.write.mode("overwrite").saveAsTable("main.retail.orders_silver")
# or: silver.write.format("delta").mode("overwrite").saveAsTable(...)
```

| Method | What it does |
|--------|----------------|
| `dropna()` | Remove rows with nulls (optionally only in some columns) |
| `fillna({...})` | Replace nulls with defaults |
| `cast("type")` | Convert types (`double`, `int`, `timestamp`, `string`) |
| `when(...).otherwise(...)` | If/else column logic |

**Analogy:** Bronze is the messy inbox. Silver is the cleaned spreadsheet ready for joins and KPIs.

### 3.7 Split strings & explode arrays (nested / semi-structured)

Official objective: *splitting, exploding arrays*.

```python
# "a,b,c" → array ["a","b","c"]
df2 = df.withColumn("tags_arr", split(col("tags"), ","))

# One array element per row (row multiplication)
df3 = df2.withColumn("tag", explode(col("tags_arr")))

# Safer if array can be null/empty: explode_outer keeps the parent row
df3 = df2.withColumn("tag", F.explode_outer(col("tags_arr")))
```

**What happens with `explode`:**

```
Before:  order_id=1, tags=[red, blue]
After:   order_id=1, tag=red
         order_id=1, tag=blue
```

**Exam trap:** `explode` on null/empty can **drop** the row; `explode_outer` keeps it with null element.

**JSON nested structs:** often use `col("payload.customer.id")` or `get_json_object` / `from_json` — know the idea: dig into nested fields, then flatten.

### 3.8 Joins (must-know set)

Official: *inner, left, broadcast, multiple keys, cross, union, union all*.

```python
# Inner join — only matching keys
inner = orders.join(customers, on="customer_id", how="inner")

# Left join — keep all orders; customer cols null if no match
left = orders.join(customers, on="customer_id", how="left")

# Multi-key join
both = orders.join(
    shipments,
    on=["order_id", "warehouse_id"],
    how="inner"
)

# Explicit condition (different column names)
both = orders.join(
    customers,
    orders.cust_id == customers.id,
    how="left"
)

# Cross join — Cartesian product (dangerous at scale)
cross = df_a.crossJoin(df_b)
# or: df_a.join(df_b, how="cross")
```

#### Broadcast join

```python
# Force broadcast of the SMALL side
result = big.join(broadcast(small), on="country_code", how="left")
```

**Analogy:**  
- Normal join = both rooms empty their filing cabinets onto a shared sorting table (shuffle).  
- Broadcast = photocopy the **small** phonebook and give every worker a copy; big table stays local.

**Exam knobs:**
- `spark.sql.autoBroadcastJoinThreshold` — max size Spark will auto-broadcast (bytes). Increase carefully; too large → driver/executor memory pressure.
- Manual `broadcast(df)` when you **know** the side is small.

#### Join result shapes (memorize)

| Join | Keeps rows from |
|------|-----------------|
| `inner` | Matches only |
| `left` | All left + matches from right |
| `cross` | Every left × every right |
| left anti (SQL) | Left rows with **no** match |
| left semi (SQL) | Left rows that **have** a match (no right cols) |

DEA outline lists inner/left/cross/broadcast. Semi/anti often appear in Spark SQL questions — still useful.

### 3.9 Union vs union all / unionByName

```python
# Same schema + same column order
all_rows = df_jan.union(df_feb)            # SQL UNION ALL semantics in Spark (keeps duplicates)
deduped  = df_jan.union(df_feb).distinct() # more like SQL UNION

# Prefer by name when column order differs
all_rows = df_jan.unionByName(df_feb)
all_rows = df_jan.unionByName(df_feb, allowMissingColumns=True)
```

| API | Exam meaning |
|-----|----------------|
| `union` | Stack rows; **keeps duplicates** (like UNION ALL) |
| `distinct` after union | Remove duplicate rows |
| `unionByName` | Align by **column name**, not position |

**Misconception:** Spark’s `DataFrame.union` is **not** SQL `UNION` (which dedups). It behaves like **UNION ALL**.

### 3.10 Deduplication

```python
# Exact full-row duplicates
df2 = df.distinct()

# Dedup by business keys (keep one row per key)
df2 = df.dropDuplicates(["order_id"])
df2 = df.dropDuplicates(["order_id", "line_id"])
```

**Bronze→Silver pattern:** often `dropDuplicates` on natural keys after cleaning nulls.

**Exam note:** `dropDuplicates` does **not** guarantee *which* duplicate survives unless you order first (window/`row_number`) — Associate level usually stops at “remove dup keys”.

### 3.11 Aggregations (`groupBy` + `agg`)

Official: *count, approximate count distinct, mean, summary*.

```python
from pyspark.sql.functions import count, countDistinct, approx_count_distinct, mean, sum as _sum

kpi = (
    orders
    .groupBy("country", "order_date")
    .agg(
        count("*").alias("orders"),
        countDistinct("customer_id").alias("unique_customers"),
        approx_count_distinct("customer_id").alias("approx_unique_customers"),
        mean("amount").alias("avg_amount"),
        _sum("amount").alias("revenue")
    )
)

# Quick profile of numeric/string columns
orders.select("amount", "qty").summary().show()
# or: orders.describe("amount", "qty").show()
```

| Function | Meaning | When exam likes it |
|----------|---------|-------------------|
| `count("*")` | Row count | Totals |
| `countDistinct("c")` | Exact distinct | Accuracy matters |
| `approx_count_distinct("c")` | Approximate distinct (HyperLogLog) | Huge data, speed OK with approx |
| `mean` / `avg` | Average | KPIs |
| `summary()` / `describe()` | Stats overview | Profiling / QA |

**Analogy:** `countDistinct` counts every unique ID carefully. `approx_count_distinct` estimates the crowd size from a smart sample of badges — faster, slightly fuzzy.

### 3.13 Built-in functions vs UDFs

```python
# GOOD — Catalyst can optimize
df.withColumn("tier", when(col("amount") > 100, lit("A")).otherwise(lit("B")))

# AVOID when a built-in exists — slower (Python row shipping)
from pyspark.sql.functions import udf

def tier(amount):
    return "A" if amount and amount > 100 else "B"

tier_udf = udf(tier, StringType())
df.withColumn("tier", tier_udf(col("amount")))
```

**Exam stance:** Prefer **Spark SQL / built-in functions**. Use UDFs only when logic cannot be expressed otherwise.

### 3.14 Higher-order functions on arrays (light touch)

Often shown in **SQL**, sometimes via `F.transform` / `F.filter` in PySpark.

```sql
-- SQL style (common on exams)
SELECT transform(tags, x -> upper(x)) AS tags_up
FROM t;

SELECT filter(tags, x -> x LIKE 'prod_%') AS prod_tags
FROM t;
```

```python
# PySpark equivalents
df.withColumn("tags_up", F.transform(col("tags"), lambda x: F.upper(x)))
df.withColumn("prod_tags", F.filter(col("tags"), lambda x: x.startswith("prod_")))
```

**When to use:** transform arrays **without** exploding to rows (cheaper when you want to keep one row).

### 3.15 Actions that bite: `collect()`, `show()`, `count()`

```python
df.count()     # OK for metrics; full scan
df.show(20)    # OK; only displays sample
df.collect()   # pulls ALL rows to the driver — dangerous on big data
rows = df.limit(100).collect()  # safer pattern when you truly need driver-side data
```

**Exam idea:** `collect()` on a huge DataFrame → driver OOM / failure. Prefer `write`, `display`/`show`, aggregations.

### 3.16 `repartition` vs `coalesce` (often adjacent to tuning)

```python
df2 = df.repartition(200)           # full shuffle; can increase or decrease partitions
df2 = df.repartition(200, "date")   # partition by key (helps later groupBy/join on date)
df2 = df.coalesce(50)               # reduce partitions; avoids full shuffle (narrow)
```

| API | Shuffle? | Typical use |
|-----|----------|-------------|
| `repartition(n)` | Yes | Increase parallelism / fix skew layout |
| `coalesce(n)` | No (usually) | Reduce partitions before write |

You rarely write these on Associate coding questions, but options may mention them next to shuffle/skew.

---

### 3.17 Tuning parameters named in the exam guide

Memorize **what they control**, not magic numbers.

| Parameter | Plain meaning |
|-----------|----------------|
| `spark.sql.shuffle.partitions` | How many tasks after a shuffle (joins/groupBy). Default often 200. Too low → fat tasks; too high → scheduling overhead. |
| `spark.default.parallelism` | Default parallelism for RDD-ish / some ops (less central than shuffle partitions for DataFrames). |
| `spark.executor.memory` / `spark.driver.memory` | Heap sizes. OOM / spill symptoms → memory or partition sizing issues. |
| `spark.sql.autoBroadcastJoinThreshold` | Max size for auto broadcast joins. |

**Related troubleshooting (Section 6):** skew, shuffle, disk spill in Spark UI — one slow task + huge max shuffle read = skew; AQE skew join handling may help.

### 3.18 End-to-end silver transform (exam-shaped)

```python
from pyspark.sql.functions import col, when, lit, explode_outer, split, broadcast

bronze = spark.table("main.retail.events_bronze")
dims   = spark.table("main.retail.country_dim")  # small

silver = (
    bronze
    .dropna(subset=["event_id", "event_ts"])
    .withColumn("event_ts", col("event_ts").cast("timestamp"))
    .withColumn("amount", col("amount").cast("double"))
    .fillna({"country_code": "ZZ"})
    .withColumn("tag_arr", split(col("tags"), ","))
    .withColumn("tag", explode_outer(col("tag_arr")))
    .dropDuplicates(["event_id", "tag"])
    .join(broadcast(dims), on="country_code", how="left")
    .withColumn(
        "is_eu",
        when(col("region") == "EU", lit(True)).otherwise(lit(False))
    )
)

(
  silver.write
    .format("delta")
    .mode("overwrite")
    .saveAsTable("main.retail.events_silver")
)
```

## 4. Frequently asked questions

**Q1. Do I need to memorize PySpark syntax perfectly?**  
No. You need to **recognize** what a snippet does and pick the correct API among options (join type, explode vs select, approx vs exact distinct, broadcast vs shuffle).

**Q2. Will the exam be Python-only?**  
No. Many items are SQL. Same concepts: filter, join, explode, aggregate, merge. Learn both “accents”.

**Q3. `filter` vs `where`?**  
Same thing in PySpark.

**Q4. When do I use broadcast?**  
When one side is **small enough** to copy everywhere and the alternative is a heavy shuffle join.

**Q5. Why is cross join dangerous?**  
Rows multiply: `N * M`. Fine for tiny dims; catastrophic for large facts.

**Q6. `countDistinct` vs `approx_count_distinct`?**  
Exact vs fast approximate. Huge cardinality + SLA → approx; finance-grade unique counts → exact.

**Q7. Is `union` deduplicating?**  
In Spark DataFrames, **no** — it keeps duplicates (UNION ALL style).

**Q8. Should I use UDFs on the exam / in production?**  
Only if built-ins cannot express the logic. Exam prefers built-ins.

**Q9. `spark.table` vs reading files?**  
In Databricks + Unity Catalog workflows, tables are the normal interface. Files appear more in ingestion (Auto Loader / COPY INTO).

**Q10. What about Window functions / `row_number`?**  
Useful in real ETL for “latest record per key”. Associate outline emphasizes dropDuplicates/aggregations more; still good to recognize `row_number` for dedup patterns.

## 5. Common misunderstandings & mistakes

| Confused pair | What people think | What is actually true | Exam trap |
|---------------|-------------------|-----------------------|-----------|
| `union` vs SQL `UNION` | Spark union dedups | Spark `union` ≈ **UNION ALL** | “How to remove dups?” → `distinct` / `dropDuplicates` |
| `inner` vs `left` | Same if dims complete | Left keeps unmatched left rows | Row-count questions |
| `explode` vs `explode_outer` | Same | Outer keeps rows when array null/empty | Lost rows after explode |
| `broadcast` always faster | Always use it | Only if side is **small**; large broadcast hurts memory | Auto threshold / OOM |
| `collect()` for debugging | Harmless | Pulls **all** data to driver | Driver OOM scenario |
| `&` vs `and` | Interchangeable | Must use `&` / `\|` with **parentheses** | Broken filters |
| `withColumn` add vs replace | Always adds | Same name **replaces** | Schema surprise |
| UDF vs built-in | UDFs are “more powerful = better” | Built-ins are faster & optimizable | Performance questions |
| `repartition` vs `coalesce` | Same | Repartition shuffles; coalesce usually does not | “Reduce partitions cheaply” |
| `countDistinct` vs `approx_count_distinct` | Same answer | Approx is faster, not exact | Pick approx for scale |

## 6. Decision cheat-sheets

### 6.1 Which join?

```
Need only matches?                    → inner
Keep all left rows?                   → left
Tiny right dimension?                 → left/inner + broadcast(right)
Need every combination?               → cross (only if both tiny)
Stack two same-schema batches?        → union / unionByName
```

### 6.2 Clean nulls?

```
Key columns must exist          → dropna(subset=[keys])
Optional fields have defaults   → fillna({...})
Wrong types from JSON/CSV       → cast(...)
Business rule flags             → when(...).otherwise(...)
```

### 6.3 Nested tags / arrays?

```
Need one row per element        → explode / explode_outer
Need to keep array, change elems→ transform / filter (higher-order)
String "a,b,c"                  → split → then explode if needed
```

### 6.4 Aggregates?

```
How many rows?                  → count("*")
How many unique IDs (exact)?    → countDistinct
How many unique IDs (huge)?     → approx_count_distinct
Average / totals                → mean / sum
Profile columns quickly         → summary() / describe()
```

### 6.5 Performance symptom → first thought

```
One task very slow, max shuffle >> median → skew (AQE skew join / salt)
Join with tiny dim still slow             → check broadcast / threshold
Driver dies after collect/toPandas        → stop collecting full DF
Too many tiny files after write           → coalesce before write / optimize later (Delta)
```

## 9. Self-check questions (with answers)

**1.** What does this return compared to a left join?  
`orders.join(customers, "customer_id", "inner")`  
**Answer:** Only orders that have a matching customer.

**2.** Why might row count drop after `explode("tags")`?  
**Answer:** Null/empty arrays drop rows; use `explode_outer` to keep them.

**3.** Spark `df1.union(df2)` — duplicates kept or removed?  
**Answer:** Kept (UNION ALL behavior).

**4.** When is `approx_count_distinct` preferred over `countDistinct`?  
**Answer:** Very large data where approximate unique counts are acceptable and speed matters.

**5.** What does `broadcast(dim)` optimize?  
**Answer:** Avoids shuffling the large side by shipping the small dimension to executors.

**6.** Fix this filter idea in PySpark: `amount > 0 and country is not null` using Column APIs.  
**Answer:** `df.filter((col("amount") > 0) & col("country").isNotNull())`

**7.** What is dangerous about `df.collect()`?  
**Answer:** Pulls all partitions to the driver; can OOM.

**8.** Bronze→silver: name three typical cleaning ops.  
**Answer:** e.g. `dropna` on keys, `cast` types, `fillna` defaults (plus dedup/join/enrichment).

**9.** Which parameter caps automatic broadcast join size?  
**Answer:** `spark.sql.autoBroadcastJoinThreshold`.

**10.** `repartition(10)` vs `coalesce(10)` — which shuffles?  
**Answer:** `repartition` shuffles; `coalesce` typically does not (when reducing).

**11.** What does `dropDuplicates(["order_id"])` do?  
**Answer:** Keeps one row per `order_id` (duplicate keys removed).

**12.** Why are built-in functions preferred over Python UDFs?  
**Answer:** Native execution + Catalyst optimization; UDFs add Python serialization overhead.
