## 2. Definitions dictionary

| Term | Plain definition |
|------|------------------|
| **Databricks** | Managed lakehouse platform: Spark compute + notebooks/jobs + catalogs + Delta storage on your cloud object store |
| **Lakehouse** | Architecture that keeps **cheap object storage** (data lake) but adds **warehouse-like reliability** (ACID, schema, SQL) |
| **Data lake** | Files in object storage (S3/ADLS/GCS); flexible, cheap; historically weak on ACID/governance |
| **Data warehouse** | Structured analytics store; strong SQL/governance; historically more expensive / less flexible for raw/ML data |
| **Bronze / Silver / Gold** | Multi-hop layers: raw → cleaned/conformed → business aggregates |
| **Delta Lake** | Open storage layer on Parquet + transaction log (`_delta_log`) giving ACID, time travel, MERGE |
| **Catalog** | Top-level namespace for databases/schemas and tables (and more under UC) |

| **Hive metastore** | Legacy metadata service for databases/tables; Databricks still supports “Hive-style” names but UC is preferred |
| **Managed table** | Databricks/UC owns the data files location and lifecycle |
| **External / unmanaged table** | Metadata in catalog; **you** own the data path; drop table ≠ delete files |
| **Parquet** | Columnar file format; files are written as immutable objects |
| **Partitioning** | Physical folders by column values (e.g. `date=2026-07-20`) |
| **Z-Ordering** | Multi-dimensional clustering of data within files to speed filtered reads (legacy/optimize path) |
| **Liquid Clustering** | Modern Delta clustering: declare cluster keys; Databricks maintains layout without rigid partitions |
| **CTAS** | `CREATE TABLE AS SELECT` — create table and fill from a query |
| **Deep clone** | Full copy of data + metadata |
| **Shallow clone** | Metadata copy; reuses source data files (cheap, linked) |
| **Auto Loader** | Incremental file ingestion with schema inference/evolution and checkpointing |
| **COPY INTO** | SQL command to load files into a Delta table (idempotent for already-loaded files) |
| **Lakeflow / DLT / LDP** | Declarative pipelines: you declare tables/views + expectations; platform manages graph, retries, infra |
| **AQE** | Adaptive Query Execution — Spark re-optimizes plan at runtime |
| **Control plane** | Databricks account/workspace UI, Jobs API, metadata services (managed by Databricks) |
| **Data plane** | Your cloud account compute + storage where data and clusters actually run |
| **`_rescued_data`** | Column Auto Loader / schema-on-read uses to stash malformed / unexpected fields instead of failing the whole batch |

## 3. Core concepts

### 3.1 What is Databricks?

**Definition:**  
Databricks is a **cloud lakehouse platform**. It runs Apache Spark (and related engines) on clusters in **your cloud account**, while Databricks operates the workspace, scheduling, security integrations, and catalog services.

**Analogy:**  
A factory park: Databricks builds the roads, security gate, and control room (**control plane**). Your machines and warehouses sit on **your land** (**data plane** / cloud subscription).

**How resources are deployed (high level)**

```
┌─────────────────────────────────────────────────────────┐
│                 CONTROL PLANE (Databricks)               │
│  Workspace UI · Jobs · Notebooks metadata · UC API      │
│  Cluster definitions · Permissions · Audit logs         │
└───────────────────────────┬─────────────────────────────┘
                            │ API / orchestration
┌───────────────────────────▼─────────────────────────────┐
│              DATA PLANE (YOUR cloud account)             │
│  Clusters / SQL warehouses  ·  Driver + executors        │
│  Object storage (ADLS/S3/GCS) with Delta tables         │
│  VNet/VPC integration, customer-managed keys (optional)  │
└─────────────────────────────────────────────────────────┘
```

**Steps when you “create a cluster”:**

1. You click Create Cluster in the workspace (control plane).
2. Databricks asks your cloud to start VMs / containers in your account (data plane).
3. Spark driver + executors come up; they read/write your storage.
4. When the job ends, compute can terminate; **data stays** in object storage.

**Advantages**

- Unified SQL + Python + Spark for batch and streaming
- Strong Delta + UC story for production governance
- Collaborative notebooks + Jobs for ops

**Limitations**

- Cost can spike if clusters idle or are oversized
- Platform features (UC, serverless, DLT) differ by cloud/SKU — check exam region assumptions
- Debugging distributed jobs still needs Spark literacy (skew, shuffle, OOM)

**Why the exam cares:** Control vs data plane questions; where data lives; who manages metastore vs compute.

### 3.2 Lakehouse vs data lake vs data warehouse

**Data lake:** Store all formats (CSV, JSON, Parquet, images) cheaply. Weak classic guarantees (no easy ACID, lots of “data swamp”).

**Data warehouse:** Clean tables, BI-friendly SQL, strong governance — historically separate copy of curated data.

**Lakehouse:** One copy on the lake + warehouse features (transactions, schema enforcement, SQL performance) via **Delta Lake** (and similar).

**The three layers (multi-hop)**

| Layer | Also called | Purpose | Typical contents |
|-------|-------------|---------|------------------|
| **Bronze** | Raw / landing | Ingest as-is; preserve history | JSON/CSV landings, Auto Loader tables, `_rescued_data` |
| **Silver** | Cleaned / conformed | Validate, dedupe, join reference data | Typed columns, quarantine bad rows, SCD patterns |
| **Gold** | Serving / marts | Business aggregates for BI/ML | KPIs, star schemas, feature tables |

**Analogy:** Bronze = unopened mail. Silver = sorted, opened, labeled. Gold = reports you send to management.

**Advantages of multi-hop**

- Replayability: rebuild Silver/Gold from Bronze
- Clear ownership and quality gates per layer
- Isolates schema drift at the edge

**Limitations**

- Extra storage and compute (more hops = more cost)
- Over-engineering for tiny projects
- Stale Gold if pipelines lag

### 3.3 Delta Lake

**Definition:**  
Delta Lake is a storage layer that stores data as **Parquet files** plus a **transaction log** (`_delta_log`) so readers/writers get **ACID transactions**, **schema enforcement/evolution**, **time travel**, and **MERGE** (upserts).

**Analogy:** Parquet files are pages of a book; `_delta_log` is the librarian’s ledger saying which pages are current after each edit.

**What you get**

- `UPDATE` / `DELETE` / `MERGE` without rewriting the whole lake manually
- Time travel: `VERSION AS OF` / `TIMESTAMP AS OF`
- `OPTIMIZE`, `VACUUM`, Z-Order / Liquid Clustering

**Advantages**

- Reliable concurrent reads/writes
- Auditability and rollback
- Works with Spark, SQL warehouses, many engines

**Limitations**

- Small-file problem if you write too often without OPTIMIZE / auto-compaction
- `VACUUM` deletes old files → can break time travel beyond retention
- Not magic: bad partitioning / clustering still hurts performance

**Mini example (explained)**

```sql
CREATE TABLE sales USING DELTA AS SELECT * FROM bronze_sales;

UPDATE sales SET amount = amount * 1.19 WHERE country = 'DE';

SELECT * FROM sales VERSION AS OF 3;
```

| Step | Statement | Purpose (what happens) |
|------|-----------|-------------------------|
| 1 | `CREATE TABLE sales USING DELTA AS SELECT * FROM bronze_sales` | **CTAS:** create a new Delta table named `sales`, copy all rows from `bronze_sales`, write Parquet files + start `_delta_log` at version 0 |
| 2 | `UPDATE ... WHERE country = 'DE'` | Change matching rows: multiply `amount` by 1.19 (e.g. add VAT). Delta does **not** edit old files in place — it writes new files and commits version 1 in the log |
| 3 | `SELECT * FROM sales VERSION AS OF 3` | **Time travel:** read the table as it looked at version 3 (if that version still exists and was not vacuumed) |

### 3.4 Catalog, Unity Catalog, and “Hive”

#### Catalog

A **catalog** is the top namespace: `catalog.schema.table` (three-level namespace under UC).

#### Unity Catalog (UC)

**Definition:** Central governance for Databricks: catalogs, schemas, tables/views/volumes/functions/models, grants, lineage, audit.

**Use cases**

- One permission model across workspaces
- Share data safely across teams
- Track lineage for compliance (GDPR-friendly ops)

**Advantages:** Central ACLs, lineage, consistent identity (account-level).  
**Limitations:** Migration from legacy Hive metastore takes planning; some older features/paths differ; workspace must be UC-enabled.

#### What is Hive in Databricks context?

**Hive Metastore** historically stored **table metadata** (name → schema → location). Apache Hive itself was a SQL-on-Hadoop engine. On Databricks, tutors often say:

> “The table is **not managed by Hive** (the compute engine) — metadata may still follow **Hive metastore conventions**.”

So:

- **Hive metastore** = metadata catalog service (legacy on Databricks)
- **Hive the query engine** = usually **not** what runs your Databricks SQL/Spark jobs (Spark does)

**Managed by Hive metastore vs not (exam language)**

| Aspect | Legacy Hive metastore workspace | Unity Catalog |
|--------|----------------------------------|---------------|
| Namespace | Usually two-level: `database.table` | Three-level: `catalog.schema.table` |
| Governance | Workspace-scoped, weaker central model | Account-level grants, lineage |
| Default recommendation | Legacy / migration path | Prefer UC for new work |

**Managed vs external tables** (separate from Hive vs UC!)

| Type | Who owns files? | `DROP TABLE` |
|------|-----------------|--------------|
| **Managed** | Databricks/UC (managed location) | Removes metadata **and** data |
| **External** | You (path you specify) | Removes metadata only; files remain |

**Misconception cleanup:** “Not managed by Hive” ≠ “unmanaged table”. Tutor meant **metadata/governance plane**, not managed-vs-external storage.

### 3.5 Parquet files are immutable — why?

**Definition:** Once a Parquet (or Delta data) file is written to object storage, Spark/Delta **does not edit bytes in place**. Updates create **new files**; the transaction log points readers to the new set.

**Why**

- Object stores (S3/ADLS) are not great at random byte updates
- Immutability enables safe concurrent readers (MVCC-style via the log)
- Failed writes leave old files intact; commit is atomic in `_delta_log`

**Advantages:** Reliability, time travel, simpler concurrency.  
**Limitations:** Extra storage until `VACUUM`; many tiny files hurt listing/IO → need OPTIMIZE / clustering / auto-compact.

### 3.6 Partitioning, Z-ORDER, Liquid Clustering

#### Partitioning

Physical directories by column (e.g. `ingest_date`).

**Advantages:** Fast prune when filters match partition columns; classic pattern for date.  
**Limitations:** Too many partitions (high cardinality like `user_id`) → millions of folders/files; uneven partitions; partition evolution pain.

#### Z-ORDER indexing (OPTIMIZE ZORDER BY)

Rewrites data so related values for multiple columns are colocated in the same set of files (multi-dimensional clustering).

**Analogy:** Sorting a library so books that share *genre AND year* sit near each other — fewer shelves to walk.

**Advantages:** Speeds multi-column filters without insane partition counts.  
**Limitations:** Rewrite cost; you choose columns carefully; superseded in many new tables by Liquid Clustering.

#### Liquid Clustering

Declare cluster keys on a Delta table; Databricks incrementally clusters as data lands — **no** rigid Hive-style partitions required for those keys.

**Advantages:** Adapts as data grows; avoids partition explosion; simpler ops.  
**Limitations:** Feature availability/version dependent; still need good key choice; not a free lunch for every query pattern.

**Exam fork:** Prefer Liquid Clustering for new Delta tables when available; use partitioning for strong, low-cardinality filters (often date); Z-ORDER when optimizing existing partitioned/non-liquid tables for multi-column predicates.

### 3.7 CTAS, inserts, overwrite, MERGE

#### CTAS — `CREATE TABLE AS SELECT`

```sql
CREATE TABLE gold.daily_revenue AS
SELECT order_date, SUM(amount) AS revenue
FROM silver.orders
GROUP BY order_date;
```

**Purpose of this query (step by step)**

1. Read all rows from `silver.orders` (cleaned orders).
2. Group rows that share the same `order_date`.
3. For each date, compute `SUM(amount)` and name it `revenue`.
4. **Create** a new table `gold.daily_revenue` and **fill it** with those aggregated rows in one shot.

**Why use it:** Materialize a Gold mart so BI tools query a small aggregate instead of rescanning Silver every time.

**Use cases:** Quick materialization of a query result; prototyping Gold tables.  
**Advantages:** One statement, clear.  
**Limitations:** Full rebuild pattern unless combined with incremental design; be explicit about `USING DELTA` / location / UC path in production.

#### Inserting in general

| Statement | Behavior |
|-----------|----------|
| **`INSERT INTO`** | Append rows (or insert into specific partitions depending on mode) |
| **`INSERT OVERWRITE`** | Replace table or partition contents with query result |
| **`MERGE INTO`** | Conditional insert/update/delete (upserts) matched on keys |

**INSERT INTO — advantages:** Simple append; good for immutable event logs.  
**Limitations:** Duplicates if you re-run without idempotency.

**INSERT OVERWRITE — advantages:** Full refresh of a table/partition; easy daily rebuild.  
**Limitations:** Easy to wipe wrong partition; expensive on huge tables; not ideal for true CDC upserts.

**MERGE — advantages:** Correct CDC / SCD-style upserts; one declarative statement.  
**Limitations:** Heavier than append; needs good keys; watch cardinality and shuffle.

```sql
MERGE INTO silver.customers t
USING bronze.customers_cdc s
ON t.customer_id = s.customer_id
WHEN MATCHED AND s.op = 'U' THEN UPDATE SET *
WHEN MATCHED AND s.op = 'D' THEN DELETE
WHEN NOT MATCHED THEN INSERT *;
```

**Purpose of this MERGE (step by step)**

| Step | Clause | Meaning |
|------|--------|---------|
| 1 | `MERGE INTO silver.customers t` | Target table to change = `t` (current Silver customers) |
| 2 | `USING bronze.customers_cdc s` | Source of changes = CDC feed `s` (inserts/updates/deletes from upstream) |
| 3 | `ON t.customer_id = s.customer_id` | Match key: same customer id → treat as same business entity |
| 4 | `WHEN MATCHED AND s.op = 'U' THEN UPDATE SET *` | If found **and** operation is Update → overwrite target columns from source |
| 5 | `WHEN MATCHED AND s.op = 'D' THEN DELETE` | If found **and** operation is Delete → remove that customer from Silver |
| 6 | `WHEN NOT MATCHED THEN INSERT *` | If customer id is **new** → insert the full source row |

**Mental picture**

```
bronze.customers_cdc (changes)     silver.customers (truth)
         │                                  │
         └────────── MERGE on id ───────────┘
              U → update row
              D → delete row
              new id → insert row
```

#### INSERT examples (explained)

```sql
-- Append new events (does NOT remove old rows)
INSERT INTO bronze.events SELECT * FROM landing_today;

-- Replace entire table contents with a fresh query result
INSERT OVERWRITE TABLE gold.daily_revenue
SELECT order_date, SUM(amount) AS revenue
FROM silver.orders
GROUP BY order_date;

-- Replace only one partition (classic pattern)
INSERT OVERWRITE TABLE silver.orders PARTITION (order_date = '2026-07-20')
SELECT * FROM staging_orders_2026_07_20;
```

| Query | Purpose |
|-------|---------|
| `INSERT INTO` | Add rows; history of appends remains (unless you delete later) |
| `INSERT OVERWRITE` (table) | Wipe table logical contents and refill from SELECT |
| `INSERT OVERWRITE` (partition) | Rebuild **only** that date/partition — safer than full wipe |

### 3.8 Deep vs shallow clones

| | **Deep clone** | **Shallow clone** |
|--|----------------|-------------------|
| **What copies** | Metadata + **all data files** | Metadata; **reuses** source data files |
| **Cost / time** | Higher | Cheap / fast |
| **Independence** | Fully independent after clone | Shares files until you modify (then diverges) |
| **Use cases** | Prod backup, migrate, isolate experiments with full copy | Dev/test quick copy, ML feature experiments |

**Advantages / limitations:** Deep = safe but slow/expensive. Shallow = fast but coupled to source file lifecycle (don’t VACUUM source carelessly while shallow clones need those files).

### 3.9 Views

| Type | Definition | Use case | Limits |
|------|------------|----------|--------|
| **View (standard)** | Saved query; runs against base tables each time | Abstraction, security via grants on view | No stored results; base table changes show up immediately |
| **Temp view** | Session-scoped | Notebook exploration | Gone when session ends |

**Exam tip:** Views don’t “contain” Delta files; tables do (unless materialized).

### 3.10 Spark’s role — easy diagram

**Definition:** Apache Spark is the **distributed compute engine**. Databricks schedules Spark on clusters; your SQL/Python DataFrame code becomes tasks on executors.

```
        You write SQL / PySpark
                 │
                 ▼
        ┌────────────────┐
        │ Spark Driver   │  plans query, coordinates
        └───────┬────────┘
                │ tasks
     ┌──────────┼──────────┐
     ▼          ▼          ▼
 Executor   Executor   Executor   ← data plane VMs
     │          │          │
     └──────────┴──────────┘
                │
                ▼
     Delta / Parquet on object storage
```

**Integration with Databricks**

- Notebooks / Jobs submit Spark apps
- SQL warehouses run Spark (Photon-accelerated where enabled)
- Structured Streaming for incremental
- AQE adjusts plans mid-query

**Advantages:** Scales out; unified batch/stream API.  
**Limitations:** Shuffle-heavy joins hurt; driver OOM on huge `collect()`; needs ops skill (skew, partitioning).

### 3.11 Querying files and `_rescued_data`

When reading semi-structured files (especially with Auto Loader / `cloudFiles` / rescued data mode), columns that **don’t match the schema** or **fail casting** can go into **`_rescued_data`** instead of failing the whole job.

**Analogy:** Airport security tray for “items that don’t fit the checklist” — flight still boards; weird items are bagged for later.

**Use cases:** Schema drift without pipeline outage; later quarantine/repair in Silver.  
**Advantages:** Resilience.  
**Limitations:** Silent quality issues if you never inspect `_rescued_data`; can hide bugs.

### 3.12 Higher-order functions and UDFs

**Higher-order functions (Spark SQL):** `transform`, `filter`, `exists`, `aggregate` on arrays — keep work in the Catalyst/Photon path.

```sql
SELECT transform(scores, x -> x * 1.1) AS bumped FROM t;
```

**Purpose (step by step)**

1. Read column `scores` (an **array** of numbers) from table `t`.
2. For **each element** `x` in that array, compute `x * 1.1`.
3. Return a new array column `bumped` (same length, values scaled up 10%).
4. Engine stays in SQL/Catalyst — usually faster than a Python UDF loop.
**UDFs (user-defined functions):** Custom Python/Scala logic registered as functions.

| | Higher-order / built-ins | Python UDF |
|--|--------------------------|------------|
| **Perf** | Usually better | Often slower (row serialization) |
| **Use when** | Array/struct logic fits SQL | Truly custom logic only |
| **Exam preference** | Prefer built-ins / higher-order | UDF as last resort |

**Pandas/Scalar iterators / Spark 3+ vectorized UDFs** are better than naive Python UDFs when you must UDF — still prefer native expressions if possible.

### 3.14 Joins, UNION, INTERSECT + explode / broadcast

#### Join types (depends on field / keys)

| Join | Keeps |
|------|--------|
| **Inner** | Rows with matches in **both** |
| **Left outer** | All left + matching right (nulls if no match) |
| **Right outer** | All right + matching left |
| **Full outer** | All from both |
| **Left anti** | Left rows with **no** match on right |
| **Left semi** | Left rows that **have** a match (no right cols) |
| **Cross** | Cartesian — dangerous at scale |

**UNION:** Stack rows (duplicates kept unless `UNION DISTINCT` / `union().distinct()`). Schemas must align (use `unionByName` when names matter).  
**INTERSECT:** Rows present in both result sets.  
**EXCEPT / MINUS:** In one, not the other.

#### Broadcast join (detail)

**What:** Spark sends a **small** table to every executor so the large table is scanned locally without a huge shuffle join.

**When:** Dimension / lookup tables that fit in memory (broadcast threshold; AQE can also convert).

**How (hint):**

```python
from pyspark.sql.functions import broadcast
df_large.join(broadcast(df_small), "id")
```

**Purpose (step by step)**

1. Mark `df_small` as a **broadcast** hint: “this side is tiny — ship a copy to every executor.”
2. Join on column `id` with `df_large`.
3. Each executor holds the small table in memory and scans its local chunks of the large table.
4. **Avoids** a full shuffle of the large table for the join (when the hint is valid).

```
Without broadcast:  both sides shuffle by id  →  heavy network
With broadcast:     small table copied once   →  large table stays local
```

**Advantages:** Huge speedup when small side is truly small.  
**Limitations:** If “small” isn’t small → executor OOM; wrong on huge dims.

#### Explode (detail)

**What:** Turns each element of an array (or each key of a map) into its **own row**.

```python
from pyspark.sql.functions import explode, explode_outer
df.select(explode("events").alias("event"))
```

**Purpose (step by step)**

1. Start with rows that have an **array** column `events` (e.g. `[click, view, buy]`).
2. `explode("events")` creates **one output row per array element**.
3. Alias that element as `event`.
4. Result: nested list → flat rows for joins/aggregations.

Example: 1 input row with 3 events → 3 output rows.

- `explode`: drops rows with null/empty arrays  
- `explode_outer`: keeps them with nulls  

**Use cases:** Nested JSON, click arrays, multi-value attributes.  
**Limitations:** Can multiply rows massively → cost, skew, downstream fan-out.

### 3.15 Spark AQE (Adaptive Query Execution) — whole scenario

**Definition:** After some stages finish, Spark **revises** the physical plan using runtime stats (real sizes, skew).

**Scenario**

1. You join `fact_orders` (estimate wrong in catalog stats) with `dim_customer`.
2. Static plan chooses a sort-merge join and 200 shuffle partitions.
3. At runtime AQE sees `dim_customer` is only 20 MB → **converts to broadcast join**.
4. AQE also sees one skewed `customer_id` → **splits skewed partitions**.
5. Coalesces empty/tiny shuffle partitions → fewer tiny tasks.

**Advantages:** Fixes bad estimates; skew handling; fewer small tasks.  
**Limitations:** Not a substitute for good keys/clustering; can make plans harder to reason about; still enable/understand configs for exams/prod.

### 3.16 Data ingestion: LakeFlow, COPY INTO, Auto Loader

#### Lakeflow (ingestion + pipelines family)

Databricks **Lakeflow** is the product umbrella for reliable data movement and declarative pipelines (ingestion + transform). For the exam, focus on:

- **Auto Loader** for files landing in cloud storage
- **Declarative pipelines (DLT/LDP)** for multi-hop transforms
- Connectors / jobs for operational ingestion patterns

#### COPY INTO vs Auto Loader

| | **COPY INTO** | **Auto Loader** (`cloudFiles`) |
|--|---------------|--------------------------------|
| **Style** | SQL command, batch-ish idempotent load | Structured Streaming + file notification/listing |
| **Tracking** | Remembers loaded files for that target | Checkpoint + rocksDB / notification queue |
| **Schema** | You manage more explicitly | Inference + evolution options |
| **Scale** | Great for moderate/periodic loads | Better for continuous / large directories |
| **Complexity** | Simpler | More knobs (options below) |

**COPY INTO — advantages:** Simple SQL, idempotent re-runs.  
**Limitations:** Less ideal as a long-running continuous ingest at massive scale vs Auto Loader.

**Auto Loader — advantages:** Incremental, scalable discovery, schema evolution, rescued data.  
**Limitations:** Need checkpoint storage; configure options carefully; understand directory listing vs notifications cost/latency.

#### Important Auto Loader options (know these)

| Option area | Examples / ideas | Why |
|-------------|------------------|-----|
| Format | `cloudFiles.format` = json/csv/parquet… | Source type |
| Schema | `cloudFiles.schemaLocation`, infer / hints | Evolution & rescue |
| Evolution | `cloudFiles.schemaEvolutionMode` | addNewColumns / fail / rescue |
| Rescue | rescued data column | Don’t fail on drift |
| Listing vs notify | directory listing vs queue (SNS/SQS, Event Grid, Pub/Sub) | Scale & cost |
| Include/exclude | path glob filters | Skip junk |
| Max files/bytes | rate limits per trigger | Protect clusters |

### 3.17 Incremental / streaming data

**Structured Streaming** processes new data continuously or as triggered micro-batches, with **checkpoints** for exactly-once / end-to-end semantics when sinks support it (Delta does).

**Pattern:** Auto Loader → Bronze Delta → Silver streaming/batch → Gold.

**Advantages:** Low latency, incremental cost vs full reload.  
**Limitations:** State, watermarks, late data; checkpoint corruption if mishandled; harder debugging than pure batch.

### 3.19 Declarative pipelines — DLT / LDP

**Definition:** You **declare** datasets and quality rules; Databricks builds the dependency graph, manages clusters (in many modes), retries, and incremental processing.

#### Object types and use cases

| Object | Use case |
|--------|----------|
| **Streaming table** | Incremental ingest / append-heavy Bronze–Silver |
| **Materialized view** | Recomputed/incremental SQL dataset for Silver/Gold |
| **View (live view)** | Logical steps without always storing (product nuances apply) |
| **Pipeline** | Unit that runs the graph on a schedule or continuously |

*(Exact names shift slightly between DLT docs and Lakeflow Declarative Pipelines — learn the idea: streaming vs materialized vs view.)*

#### Data quality: constraints & expectations

**Expectations** = declarative checks on records.

Examples:

```python
@dlt.expect("valid_id", "customer_id IS NOT NULL")
@dlt.expect_or_drop("valid_email", "email LIKE '%@%'")
@dlt.expect_or_fail("amount_nonneg", "amount >= 0")
```

**Purpose of each line (step by step)**

| Decorator | Condition | What happens on failure |
|-----------|-----------|-------------------------|
| `@dlt.expect("valid_id", ...)` | `customer_id` must not be null | Row **kept**; violation **counted** in metrics (warn/track) |
| `@dlt.expect_or_drop("valid_email", ...)` | email must look like it contains `@` | Row **dropped** from the output table |
| `@dlt.expect_or_fail("amount_nonneg", ...)` | amount must be ≥ 0 | Pipeline update **fails** (stop bad data promoting) |

Think of them as quality gates with three severities: **log**, **drop**, **stop**.

| Mode | Behavior |
|------|----------|
| expect (warn/track) | Keep row; metrics show violations |
| expect_or_drop | Drop failing rows |
| expect_or_fail | Fail the pipeline / update |

**Advantages:** Quality as code; metrics in UI; consistent across environments.  
**Limitations:** Wrong severity → either silent bad data or brittle pipelines; not a replacement for tests on business logic.

### 3.20 Declarative Automation Bundles (Databricks Asset Bundles) — deep dive

**Definition:**  
**Databricks Asset Bundles (DABs)** let you describe your Databricks project **as code** (YAML + source files): jobs, pipelines (DLT/LDP), notebooks, clusters settings, permissions — then **deploy the same definition** to `dev` / `staging` / `prod` with one CLI workflow.

People also say “declarative automation bundles” because you **declare the desired end state**; Databricks applies it (create/update resources), instead of clicking the Jobs UI by hand in every workspace.

**Analogy:**  
Like a **shipping container + packing list**. The container holds notebooks and pipeline code. The packing list (`databricks.yml`) says: “in prod, create this job, this pipeline, on this schedule.” You don’t rebuild the warehouse by hand each time — you ship the container.

#### Why bundles exist (problem they solve)

```
WITHOUT bundles (click-ops):
  Dev workspace  →  engineer clicks Job A
  Prod workspace →  another engineer clicks Job A'  (drift!)
  Git            →  notebooks only, infra forgotten

WITH bundles:
  Git repo = notebooks + databricks.yml + resources
       │
       ├── databricks bundle deploy -t dev
       └── databricks bundle deploy -t prod
              same code, different target configs
```

#### Core ideas (easy)

| Concept | Meaning |
|---------|---------|
| **Bundle** | One project package (code + resource definitions) |
| **`databricks.yml`** | Root config: name, includes, targets, variables |
| **Resources** | Things to create: `jobs`, `pipelines`, `schemas`, … |
| **Targets** | Environments (`dev`, `prod`) with different hosts/params |
| **Variables** | Parameterize catalog names, schedules, cluster sizes |
| **Deploy** | Push definition → workspace creates/updates resources |
| **Run** | Trigger a job/pipeline from the CLI after deploy |

#### Folder layout (typical)

```
retail_lakehouse/
├── databricks.yml          ← bundle brain
├── src/
│   ├── bronze_ingest.py    ← Auto Loader / notebook code
│   └── retail_dlt.py       ← DLT/LDP declarations
├── resources/
│   ├── job_daily.yml       ← optional split files
│   └── pipeline.yml
└── fixtures/               ← sample data for dev
```

#### End-to-end flow diagram

```
  Developer laptop / CI
           │
           │  1. edit code + YAML
           │  2. git commit
           ▼
      ┌─────────────┐
      │  Git repo   │
      └──────┬──────┘
             │  3. databricks bundle validate
             │  4. databricks bundle deploy -t prod
             ▼
      ┌──────────────────────────────────────┐
      │     CONTROL PLANE (target workspace) │
      │  Creates/updates:                    │
      │   • Job definitions                  │
      │   • Pipeline definitions             │
      │   • Uploads notebooks/artifacts      │
      └──────────────┬───────────────────────┘
                     │  5. schedule or bundle run
                     ▼
      ┌──────────────────────────────────────┐
      │     DATA PLANE                         │
      │  Clusters run Spark / DLT tasks        │
      │  Read/write Delta in your storage      │
      └──────────────────────────────────────┘
```

#### Annotated `databricks.yml` (what each part is for)

```yaml
# databricks.yml (illustrative — learn the shape, not memorize every key)
bundle:
  name: retail_lakehouse          # project name in Databricks

variables:
  catalog:
    default: main_dev             # default UC catalog for this bundle
  job_schedule:
    default: "0 6 * * *"          # cron: 06:00 daily

targets:
  dev:
    default: true
    workspace:
      host: https://dbc-XXXX.cloud.databricks.com
    variables:
      catalog: main_dev           # override: use dev catalog
  prod:
    workspace:
      host: https://dbc-YYYY.cloud.databricks.com
    variables:
      catalog: main_prod          # override: use prod catalog
      job_schedule: "0 5 * * *"   # prod runs earlier

resources:
  pipelines:
    retail_pipeline:
      name: retail_pipeline
      catalog: ${var.catalog}     # from variables / target
      target: silver              # schema/target for pipeline tables
      libraries:
        - notebook:
            path: ./src/retail_dlt.py
      channel: CURRENT

  jobs:
    daily_silver_gold:
      name: daily_silver_gold
      schedule:
        quartz_cron_expression: ${var.job_schedule}
        timezone_id: Europe/Berlin
      tasks:
        - task_key: run_pipeline
          pipeline_task:
            pipeline_id: ${resources.pipelines.retail_pipeline.id}
        - task_key: refresh_gold_sql
          depends_on:
            - task_key: run_pipeline
          notebook_task:
            notebook_path: ./src/gold_refresh.py
```

**Purpose of this YAML (step by step)**

1. **`bundle.name`** — names the project so deploys are tracked.
2. **`variables`** — shared knobs (catalog, schedule) so you don’t hardcode prod values in code.
3. **`targets.dev` / `targets.prod`** — different workspace URLs + variable overrides (dev catalog vs prod catalog).
4. **`resources.pipelines`** — declare a DLT/LDP pipeline pointing at your notebook; deploy creates/updates that pipeline object.
5. **`resources.jobs`** — declare a scheduled job with two tasks: run the pipeline, then run a Gold notebook **only after** the pipeline succeeds (`depends_on`).
6. **`${resources.pipelines...id}`** — wire the job to the pipeline **created by the same bundle** (no copy-paste of IDs).

#### Common CLI commands (what they do)

| Command | Purpose |
|---------|---------|
| `databricks bundle init` | Scaffold a new bundle from a template |
| `databricks bundle validate` | Check YAML/resources before deploy |
| `databricks bundle deploy -t dev` | Create/update resources in **dev** workspace |
| `databricks bundle deploy -t prod` | Same for **prod** |
| `databricks bundle run daily_silver_gold -t prod` | Trigger the job now |
| `databricks bundle destroy -t dev` | Tear down resources (careful in prod) |

#### Use cases

- Promote the **same** Bronze→Silver→Gold pipeline from lab to production  
- CI/CD: on merge to `main`, deploy to staging; on tag, deploy to prod  
- Keep schedules, cluster sizes, and catalog names **reviewed in Git**  
- Onboard new engineers: clone repo → `bundle deploy -t dev` → working stack  

#### Advantages

- Less environment drift (Jobs UI click-ops)  
- Reviewable changes (PRs on YAML + code)  
- One definition → many targets  
- Fits Germany enterprise expectation: IaC / auditability  

#### Limitations

- Learning curve (YAML schema, sync state)  
- Secrets must use secret scopes / CI secrets — never commit tokens  
- Some workspace-only experiments are still faster in the UI first, then “bundle-ize”  
- Destroy/deploy mistakes in prod hurt — use careful targets and approvals  

#### Bundle vs Jobs UI vs “just notebooks”

| Approach | Good for | Weak at |
|----------|----------|---------|
| Notebooks only | Learning, spikes | Repeatable prod deploys |
| Jobs UI clicks | Quick one-off schedule | Multi-env parity, review |
| **Asset Bundles** | Team production + CI/CD | Tiny personal sandboxes |

#### Mini scenario (what will happen)

1. You change an expectation in `retail_dlt.py` and bump the Gold notebook.  
2. `bundle validate` → YAML OK.  
3. `bundle deploy -t prod` → control plane updates pipeline + job definitions; uploads new notebook revisions.  
4. Next schedule (05:00 Berlin) → job starts → pipeline task runs Spark in **data plane** → Gold task runs → BI sees new metrics.  
5. If pipeline expectations `fail`, Gold task does not run (`depends_on`).

### 3.22 `spark.sql` vs `spark.table`

| API | Meaning |
|-----|---------|
| `spark.sql("SELECT ...")` | Run a SQL string; returns DataFrame |
| `spark.table("catalog.schema.t")` | Load a table by name as DataFrame |

Both interoperate — SQL and DataFrame are the same engine underneath.

```python
df = spark.table("main.silver.orders")
df.filter("amount > 0").createOrReplaceTempView("o")
spark.sql("SELECT date, SUM(amount) FROM o GROUP BY date").show()
```

**Purpose (step by step)**

1. `spark.table(...)` — load Unity Catalog table `main.silver.orders` as a DataFrame (no SQL string yet).  
2. `filter("amount > 0")` — keep only positive amounts.  
3. `createOrReplaceTempView("o")` — register that filtered DataFrame as a temporary SQL name `o` for this session.  
4. `spark.sql("SELECT date, SUM(amount) ...")` — aggregate in SQL against `o`.  
5. `.show()` — print results to the notebook (driver collects a sample/display).  

**Takeaway:** DataFrame API and SQL are two doors into the **same** Spark engine.

### 3.23 DELETE HISTORY vs VACUUM

| Operation | What it does | Effect on time travel |
|-----------|--------------|------------------------|
| **Describe / query history** (`DESCRIBE HISTORY`) | Shows transaction history metadata | Read-only |
| **Deleting history?** (careful wording) | People often mean removing old **versions’ usability** | — |
| **`VACUUM`** | Physically deletes **unreferenced data files** older than retention | You **cannot** time travel to vacuumed versions; frees storage |

**Critical:** `DELETE` on a table removes rows (new transaction). **`VACUUM`** cleans old files. They are not the same.

Default retention often **7 days** — lowering + vacuuming is dangerous if readers need older versions.

**Advantages of VACUUM:** Cost control, compliance deletion of old files.  
**Limitations:** Breaks deep time travel; never vacuum below retention while readers need history; concurrent writers need care.

### 3.26 Mini hands-on — what will happen

**Goal:** Land JSON → Bronze → Silver with one expectation-style check → Gold aggregate.

1. **Upload** sample JSON files to a cloud path `.../landing/orders/`.
2. **Auto Loader** reads new files into `bronze.orders` (Delta).  
   - *What happens:* New files discovered; schema inferred; bad fields may land in `_rescued_data`; checkpoint advances so files aren’t reprocessed.
3. **Silver** job reads Bronze, casts types, drops null `order_id`, writes `silver.orders`.  
   - *What happens:* Cleaner table; row counts may drop; duplicates removed if coded.
4. **Gold** `CTAS` or incremental agg into `gold.orders_daily`.  
   - *What happens:* Business-ready metrics; BI can query without touching raw JSON.
5. Run **`DESCRIBE HISTORY silver.orders`** then a mistaken overwrite; **time travel** back.  
   - *What happens:* You recover pre-mistake version **until** VACUUM removes files.
6. **OPTIMIZE** / cluster keys on Silver.  
   - *What happens:* Fewer small files; filters on cluster keys read less data.

## 4. Frequently asked questions

**Q: Is Databricks just Spark hosting?**  
A: Spark is the engine, but Databricks adds Delta, UC, Jobs, SQL warehouses, Auto Loader, declarative pipelines, and governance.

**Q: Do I need partitions if I use Liquid Clustering?**  
A: Often no for those keys — Liquid replaces many partition use cases. Date partitions sometimes still appear by habit/policy.

**Q: Why did my tutor say “not managed by Hive”?**  
A: Spark runs the query; Hive metastore (legacy) or Unity Catalog stores metadata. “Hive” ≠ the compute engine here.

**Q: Shallow clone then VACUUM source — safe?**  
A: Dangerous. Shallow clones reference source data files.

**Q: When MERGE vs INSERT OVERWRITE?**  
A: MERGE for upserts/CDC; OVERWRITE for full partition/table refresh.

**Q: Auto Loader or COPY INTO for daily dump of 20 files?**  
A: COPY INTO is often enough. Auto Loader shines with continuous landing / large trees / schema drift.

**Q: Does VACUUM delete table rows I just DELETE’d?**  
A: DELETE only tombstones via new versions; VACUUM later removes obsolete files after retention.

**Q: Inner join vs left semi?**  
A: Semi = existence filter without right-hand columns; often cheaper.

**Q: Why is my join slow?**  
A: Skew, missing broadcast opportunity, wrong join keys/types, tiny-file scans, no predicate pushdown.

**Q: spark.sql vs DataFrame — which is “better”?**  
A: Same optimizer. Choose readability; many teams mix both.

## 5. Common misunderstandings & mistakes

| Confused pair | What people think | What is actually true | Exam trap |
|---------------|-------------------|-----------------------|-----------|
| Lake vs lakehouse | Same thing | Lakehouse = lake storage + warehouse reliability (Delta) | “Warehouses are obsolete” oversimplifies |
| Managed by Hive vs managed table | Same | Hive metastore ≠ managed storage lifecycle | DROP behavior questions |
| DELETE vs VACUUM | Same cleanup | DELETE = row-level txn; VACUUM = file GC | Time travel after vacuum |
| Deep vs shallow clone | Both full copies | Shallow shares files | Cost / independence |
| INSERT INTO vs OVERWRITE | Both “load data” | Append vs replace | Accidental wipe |
| View vs table | Views store data | Views store queries (unless materialized) | Storage/ACL questions |
| Z-ORDER vs partition | Same | Partition = folders; Z-ORDER = in-file clustering | High-cardinality partition fail |
| Broadcast always good | Always faster | Only if small side fits memory | OOM |
| AQE replaces modeling | Set and forget | Helps, doesn’t fix bad models | Skew root cause |
| Control plane holds my Parquet | Yes | Data plane / your storage holds files | Residency / security |
| `_rescued_data` = error log table | Separate system | Column in the row/batch | Ignoring it silently |
| DLT expectations always drop | All fail rows dropped | warn / drop / fail modes differ | Pipeline “passed” with bad data |

## Appendix C — Query cookbook (purpose step by step)

Use this when the exam shows a snippet and asks “what does this do?”

### C1. COPY INTO

```sql
COPY INTO main.bronze.orders
FROM 'abfss://landing@storage/orders/'
FILEFORMAT = JSON
COPY_OPTIONS ('mergeSchema' = 'true');
```

| Step | What it does |
|------|----------------|
| 1 | Target table: `main.bronze.orders` (Delta) |
| 2 | Source path: cloud landing folder of JSON files |
| 3 | Read as JSON |
| 4 | `mergeSchema` allows new columns to be added if files evolved |
| 5 | Tracks which files were already loaded → **re-run is idempotent** for those files |

### C2. Clones

```sql
CREATE TABLE main.dev.orders_shallow SHALLOW CLONE main.prod.orders;
CREATE TABLE main.backup.orders_deep DEEP CLONE main.prod.orders;
```

| Query | Purpose |
|-------|---------|
| SHALLOW CLONE | Fast: copy metadata only; still reads prod’s data files |
| DEEP CLONE | Slow/safer: copy metadata **and** data files into new location |

### C3. History, time travel, optimize, vacuum

```sql
DESCRIBE HISTORY main.silver.orders;
SELECT * FROM main.silver.orders VERSION AS OF 12;
SELECT * FROM main.silver.orders TIMESTAMP AS OF '2026-07-01T00:00:00';
OPTIMIZE main.silver.orders ZORDER BY (customer_id, order_date);
VACUUM main.silver.orders RETAIN 168 HOURS;
```

| Statement | Purpose |
|-----------|---------|
| `DESCRIBE HISTORY` | List commits/versions (who/what/when) — **does not delete** |
| `VERSION AS OF` | Read table at a past version |
| `TIMESTAMP AS OF` | Read table as of a past time |
| `OPTIMIZE ... ZORDER BY` | Compact/rewrite files so filters on those columns scan less |
| `VACUUM ... RETAIN 168 HOURS` | Delete unreferenced files older than 7 days — **limits** time travel |

### C4. Set Liquid Clustering (conceptual)

```sql
CREATE TABLE main.silver.orders (
  order_id BIGINT,
  customer_id BIGINT,
  order_date DATE,
  amount DOUBLE
) USING DELTA
CLUSTER BY (customer_id, order_date);
```

**Purpose:** Create Delta table and declare cluster keys so Databricks can liquid-cluster data for those filters — avoid partition explosion on high-cardinality keys.

### C5. Joins / set ops (cheat meanings)

```sql
-- Inner: only matching ids
SELECT * FROM orders o INNER JOIN customers c ON o.customer_id = c.id;

-- Left: all orders; customer cols null if no match
SELECT * FROM orders o LEFT JOIN customers c ON o.customer_id = c.id;

-- Anti: orders with no customer match (orphans)
SELECT * FROM orders o LEFT ANTI JOIN customers c ON o.customer_id = c.id;

-- Semi: orders that have a customer (existence), no customer columns
SELECT * FROM orders o LEFT SEMI JOIN customers c ON o.customer_id = c.id;

-- Union all rows (duplicates kept)
SELECT * FROM a UNION ALL SELECT * FROM b;

-- Intersect: rows in both
SELECT * FROM a INTERSECT SELECT * FROM b;
```

### C6. Auto Loader (PySpark) — what each piece is for

```python
(df := spark.readStream
  .format("cloudFiles")
  .option("cloudFiles.format", "json")
  .option("cloudFiles.schemaLocation", "/Volumes/main/ops/schemas/orders")
  .option("cloudFiles.schemaEvolutionMode", "addNewColumns")
  .load("abfss://landing@storage/orders/")
).writeStream \
  .option("checkpointLocation", "/Volumes/main/ops/checkpoints/orders") \
  .trigger(availableNow=True) \
  .table("main.bronze.orders")
```

| Piece | Purpose |
|-------|---------|
| `readStream` + `cloudFiles` | Auto Loader incremental file source |
| `schemaLocation` | Where inferred schema is stored/evolved |
| `schemaEvolutionMode` | How to handle new fields |
| `checkpointLocation` | Exactly-once progress; **do not delete casually** |
| `trigger(availableNow=True)` | Process all available files then stop (common job pattern) |
| `.table(...)` | Sink into Delta Bronze table |
